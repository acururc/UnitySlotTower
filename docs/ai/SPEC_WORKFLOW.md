# 軽量仕様ワークフロー

大きな機能・仕様変更・大きな修正だけに使う。小さな修正は直接行う。

## 段階と完了条件

| 段階 | 成果物 | 次へ進む条件 |
| --- | --- | --- |
| 仕様 | `specs/NNN-name/spec.md` | 重要な未決事項がない |
| 承認 | `spec.md` の承認欄 | ユーザーが現行specと検証方法を明示的に承認 |
| 計画 | `plan.md`, `tasks.md` | タスクが検証可能な単位に分かれている |
| 実装・検証 | コード/アセット、`tasks.md` のチェックと結果 | 受け入れ条件の検証が実際に通る |

- 番号は `specs/` の既存最大値+1。名前は英小文字とハイフン。
- 聞き取りは結果を左右する質問を1つずつ。回答はすぐ spec に反映する。わからない回答は後続段階を止める。
- spec を変えたら承認は無効。再提示して承認を取り直す。
- plan/tasks/実装の各段階で spec の要求を複製せず、要求ID（FR-001 等）で参照する。

## spec.md 雛形

```markdown
# <機能名>

状態: 聞き取り中 | 承認済み
承認: <YYYY-MM-DD、承認範囲（例: FR-001〜FR-010 と検証方法）> / 未承認

## 目的
## 確定した決定（ユーザー回答）
## 要求
- FR-001: <観測可能な振る舞い>
## 受け入れ条件と検証方法
- AC-001 (FR-001): <手順・期待結果・使う検証（EditModeテスト / PlayModeテスト / Editor画像 / プレイヤー）>
## 範囲外
## 未決事項
```

## plan.md / tasks.md

- plan: 方針、影響するファイル/アセット/asmdef、データ構造、リスク、検証手段。
- tasks: `- [ ] T001 (FR-001) <作業> — 検証: <方法>`。完了時は `[x]` と実際の結果（テスト件数等）を書く。
