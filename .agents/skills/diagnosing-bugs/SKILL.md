# バグ診断ループ

出典: mattpocock/skills `diagnosing-bugs`（MIT）をこのプロジェクト向けに調整。各段階を飛ばすときは理由を述べる。

## 1. フィードバックループを作る（最重要）
仮説を立てる前に、**このバグで赤くなる1つのコマンド**を用意し、実際に1回実行して出力を示す。条件: ユーザーの症状そのものを判定する／毎回同じ結果／速い／無人で回せる。
作り方の優先順:
1. 症状を再現する失敗テスト（Core なら EditMode、実時間・入力・遷移なら PlayMode）。乱数はシード固定、時間は固定刻みで決定的にする。
2. Editor上の再現: `Invoke-UnityMcp.ps1` でシーンを開き Play → Console（`editor console --type error`）やスクリーンショットで判定。
3. プレイヤー固有なら `Build-UnityPlayer.ps1` → `Test-UnityPlayer.ps1`。
4. 確率・スロット系の「ときどき違う」は多数回シミュレーション（全数検査・統計）で再現率を上げる。
5. 目押しなど人の操作が必須なら、手順と確認項目をユーザーに渡して結果を返してもらう（最終手段）。
ループが作れなければ止まって、試したことを列挙し、ログ・再現手順・動画などを依頼する。ループなしで仮説に進まない。

## 2. 再現と最小化
ユーザーの言う症状と同じ失敗かを確認する（近くの別バグではないか）。入力・手順・データを1つずつ削り、どれを外しても緑になる最小の再現にする。

## 3. 仮説
検証前に 3〜5 個の反証可能な仮説を順位付けして示す（「Xが原因なら、Yを変えると消える」）。ユーザーの知見で順位が変わることが多い。返答待ちで止まらない。

## 4. 計測
各プローブは特定の仮説に対応させ、一度に1変数だけ変える。ログには `[DEBUG-xxxx]` の固有タグを付ける。性能問題はログでなく Profiler 等で基準値を測ってから比較する（測定なしに速くなったと言わない）。

## 5. 修正と回帰テスト
正しいシーム（実際のバグの流れを再現できる境界）があれば、最小再現を失敗テストにして赤を確認 → 修正 → 緑を確認 → 元のループも再実行。正しいシームがなければ、それ自体を設計上の所見として報告する。

## 6. 後片付け
- 元の再現が再発しない／回帰テストが通る（`unity-verify` の形式で件数を報告）
- `[DEBUG-` タグを grep して全削除、使い捨てのシーン・スクリプトを削除（.meta も一緒に）
- Unity自動化を停止し、正しかった仮説をコミットメッセージか報告に残す
