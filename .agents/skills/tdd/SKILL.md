# テスト駆動開発（Unity / NUnit）

出典: mattpocock/skills `tdd`（MIT）をこのプロジェクト向けに調整。テスト実行と報告は `unity-verify` に従う。

## 良いテスト
- 公開インターフェース越しに振る舞いを検証する。内部構造が変わっても壊れない。テスト名は「何ができるか」（例: `Bonus_Is_Awarded_When_Three_Sevens_Align`）。
- 期待値は独立した根拠（specのAC・手計算の具体値・既知のリテラル）から取る。実装と同じ計算で期待値を作る自己同語反復テストは書かない。
- 1テスト1論理アサーション。AC番号がある場合はテスト名か `[Description]` に残す。

## シーム（テストを置く境界）
- 原則はCore層の公開API（`UnitySlotTower.Core`）で、`Tests/EditMode` から検証する（`specs/001-slot-tower-defense/plan.md` の構成）。実時間・入力・シーン遷移が本質の場合だけ `Tests/PlayMode`。
- テストを書く前に、対象シームとそれぞれが「捕まえるもの／見逃すもの」を1行ずつ示してユーザーと合意する。tasks.md に検証方法が既に明記されていればそれを合意済みとみなす。
- モックは境界だけ: 乱数（シード固定の `System.Random` か抽選器インターフェース）、時間（固定刻みのtick）、ファイル（CSVは文字列やテスト用フィクスチャで渡す）。自前のCoreクラスはモックせず本物を使う。
- MonoBehaviour・private メソッド・呼び出し回数を検証しない。それが必要に見えたら、ロジックをCoreへ移すべき兆候として扱う。

## ループの規則
1. **red**: 失敗するテストを1つ書き、EditModeで実行して期待どおり失敗することを確認する（コンパイルエラーは red ではない。先に最小の型・シグネチャを用意する）。
2. **green**: 通るだけの最小実装をする。先のテストを見越した機能を足さない。
3. 再実行して green を確認し、次のスライスへ。テストを先にまとめて書く水平分割はしない。
4. リファクタリングはループ外（タスク完了後のレビュー段階）で行い、全テスト green を保つ。

`editor tests` にテスト名の絞り込みはないため、該当モード全体を流す。結果は `poll-test ... --failed-only` で失敗分の詳細だけ取り、各サイクルで `summary.total/passed/failed` を報告する。
